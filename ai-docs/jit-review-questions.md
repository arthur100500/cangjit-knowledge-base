# Answers to the JIT review questions

- **Outer TypeInfo:** For ordinary class/interface virtual dispatch, `CompileInvoke.cpp` now always requests the selected method's enclosing TypeInfo from `CJ_MCC_GetMethodOuterTI`, matching native library mode. This supports implementations in precompiled libraries that are absent from the JIT package's CHIR. The separate auto-environment path remains unchanged. `GlobalContext` no longer builds or caches a package-local subtype graph. Native executable mode still has its own package-local optimization; a cross-package counterexample is recorded in `ai-issues/037-jit-review-037.md`.
- **`Compilers/CompileFunction.h`:** This was a stale duplicate of `Compilers/Function/CompileFunction.h`; reference/include search found no implementation or callers for its `Compile(std::ostream&)` declaration. The duplicate was removed. The actual function compiler uses `CompileToAddress` and `Compile(FunctionContext&)`.
- **Runtime symbol casts:** `JitRuntimeBindings` returns an untyped `void*` obtained from dynamic symbol lookup; `X86_64Compiler.cpp` casts it to `decltype(&RunCJTask)` etc. A bare `*` alone cannot convert `void*` to a callable function pointer. Typed bindings can centralize the platform-specific conversion and avoid repeated casts; they do not eliminate the boundary with `dlsym`/`FindCJSymbol`.
- **Paths:** `EnsureStandardPackage` now joins paths with `std::filesystem::path`. The compiler also provides `Cangjie::FileUtil::JoinPath` and `GetDirPath`. Both call `Normalize`, which collapses repeated separators and stops at NUL; current runtime-directory extraction preserves the original substring. Replacing it would therefore change edge-case behavior.
- **Existing compilation-error enum:** `Compilers/Context/JitFailure.h` defines `JitFailureKind` for internal compilation failures, while `Types.h::CompilationError` wraps the outward diagnostic text (including AsmJit errors). Reuse or unify only if the external result can still represent all diagnostics; no claim that one enum already covers them all.
- **FunctionContext:** It owns per-function emission state and coordinates value locations, metadata and errors; its label helpers are explicitly accepted as small. Moving heavyweight type/finalizer logic elsewhere should preserve that ownership and failure propagation. `FunctionContext.cpp` itself has not yet been reviewed by the user, per the explicit source comment.
  A possible split is `TypeInfoResolver` for concrete/template lookup and emitted TypeInfo loads, `SafepointRecorder` for liveness-to-metadata conversion, `ExceptionLandingEmitter` for landing pads, and `LocalFinalizerEmitter` for lifetime analysis and emitted removals. `FunctionContext` would retain shared per-function state, accessors and labels. Ownership, failure propagation and cross-block lifetime need review before moving code.
- **Stack growth and allocation:** See `jit-metadata-layout.md` and `jit-function-stub.md`. The runtime-side ABI rationale beyond the observed stack-root encoding is not independently established.
