# How does the JIT use compilation failures, and when are assertions appropriate?

As inspected 2026-11-24, `src/JIT/X86_64/Compilers/Function/CompileFunction.cpp` collects the first `FunctionContext` failure or AsmJit error and returns a `CompilationResult`. It does not publish code after these failures. Publication can also fail while allocating executable memory, generating metadata or registering lazy call sites; it releases the allocated code on relevant failures.

For eager `user.main`, `X86_64Compiler::CompileUserMain` reports `JIT compilation failed: <message>` and sets the output stream bad bit through `ReportError`; `Compile` does not run an invalid entry. For a lazy function, `FunctionResolver` and `FunctionRecord` retain failure details; `CompileFunctionStub.cpp:ResolveAndPatch` prints `JIT lazy compilation failed: <message>` then aborts. Therefore current lazy errors improve diagnostics and prevent execution of bad code, but they do not provide recovery or fallback to the user. The FAILED state preserves the reason for a later resolution at the resolver API level; normal lazy-stub execution aborts at its first failure.

Unsupported operations, calling conventions and signatures, missing runtime symbols, assembler errors, memory allocation, and metadata size/representation limits are real failure cases, not necessarily compiler bugs. `include/cangjie/Utils/CheckUtils.h` defines `CJC_ASSERT` as a non-checking expression evaluation when `NDEBUG` is set without `CMAKE_ENABLE_ASSERT`. Replacing a real failure with that assertion alone risks publishing or executing invalid machine code in such builds. Proven internal invariants can use assertions; whether internal error-return plumbing is worth keeping is a separate API/design question. Alternatives include always-on fatal errors at a boundary, or a structured error propagated to a caller that can recover; the current code only implements the former behavior for lazy stubs, with structured propagation inside the compiler.
